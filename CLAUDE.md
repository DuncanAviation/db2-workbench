# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DB2 Workbench is a VS Code extension (publisher `DuncanAviation`) for running SQL and stored procedure calls against IBM DB2 for i (AS/400) databases over ODBC, with an inline results panel, connection management, and SQL autocomplete.

## Commands

```
npm run init      # npm i
npm run compile    # tsc -p ./ (outputs to out/)
npm run watch      # tsc -watch -p ./
npm run lint       # eslint src
npm run pretest    # compile + lint
npm test           # vscode-test — runs out/test/**/*.test.js (compile first)
npm run test:unit  # mocha out/**/*.spec.js — the co-located unit tests (compile first); 20s timeout, since CI's Windows runner is ~10x slower on first-use work such as the SQL parser warming up
npm run test:webviews  # vitest + jsdom over webviews/**/*.spec.tsx (no compile needed)
npm run test:webviews:browser  # vitest browser mode over webviews/**/*.browser.spec.tsx in headless Chromium (needs `npx playwright install chromium` once)
npm run build-exe  # vsce package --pre-release (append `-- --target win32-x64` etc. for one platform); bundles out/extension.js, then postbuild-exe reruns tsc
```

To run/debug the extension, use the "Run Extension" launch config (F5) — it builds via the default task (`watch`) and opens an Extension Development Host window.

Four separate suites. Unit tests for anything that doesn't need the VS Code API are **co-located `*.spec.ts`** next to the module they cover (e.g. `src/schema-conversion/table-resolver.spec.ts`), written with mocha + chai and run by `npm run test:unit` against `out/**/*.spec.js` — this is where most new tests belong, and it's why the pure modules (`table-resolver`, `import-groups`, `sql-import-converter`) are kept free of `vscode`/`odbc` imports. Integration tests that need a real extension host go under `src/test/**/*.test.ts` and must compile to `out/test/**/*.test.js` to be picked up by `.vscode-test.mjs`. Webview components are tested by the third suite, co-located `webviews/**/*.spec.tsx` written against vitest in jsdom, and the few gestures that need real layout by the fourth, `webviews/**/*.browser.spec.tsx` in headless Chromium (see "Webviews are React apps bundled by esbuild" below). `src/test-layout.spec.ts` fails the unit suite if a file lands in the wrong suite's reach: a `*.test.ts` outside `src/test/`, a `*.spec.ts` inside it, a `webviews/` spec that doesn't import `vitest`, or a `src/` spec that does.

## Architecture

### Extension as a lazy service locator

`src/extension.ts` defines `Extension`, a single instance (`export let extension`) created in `activate()`. It has no real logic itself — it's a container of lazily-constructed singletons, each exposed as a getter using the `return this._x ??= new X(this)` pattern (init-on-first-access, cached after):  `configurations`, `secrets`, `globalStates`, `connections` (`DbConnections`), `memoryCache`, `eventManager`, `infoManager`, `connectionsViewProvider`, `resultsViewProvider`, `completionProvider`, `connectionEditorProvider`. Every other class takes `extension: Extension` in its constructor and reaches sibling services through it rather than importing them directly — when adding a new component, wire it into `Extension` the same way instead of instantiating it elsewhere.

### Event-driven connection lifecycle (no direct coupling between DB layer and UI)

`DbConnections` (`src/database/db-connections.ts`) never talks to the UI directly. Every state change fires a `DbConnectionEvent` (`src/events/db-connection-event.ts`) through `EventManager` (`src/events/event-manager.ts`, a thin wrapper over `vscode.EventEmitter`). `DbType` values: `CONNECTING → CONNECTED`, `EXECUTING → RESULT|ERROR`, `FETCHING → FETCHED`, `LIBRARY_LIST_CHANGED`, `HISTORY_ONLY`, `CLOSED`, `READY`. `LIBRARY_LIST_CHANGED` carries the session's new `connectionInfo`; it is deliberately not `CONNECTED`, whose listeners treat it as a lifecycle step. Events carry a `key` — always the SQL document's `uri.toString()` — used to correlate events to a specific editor tab. `WorkbenchViewProvider` and `InfoManager` both subscribe via `extension.eventManager.onEvent()` and react to `event.dbType`; adding a new UI reaction to connection state means listening for these events, not calling into `DbConnections` reactively.

### One results "session" per open SQL file

`WorkbenchViewProvider` (`src/views/workbench-view-provider.ts`) keeps a `Map<uri, SqlSession>` (`sqlSessions`). A session tracks rows, query/connection history (bounded by `historyCount` setting), cursor state, and the owning `ConnectionConfig`. The "active" session follows the active text editor (or manual selection in the sidebar session list) via `activeUri`/`setActiveUri()`. Rendering is funneled through an rxjs `Subject` + `concatMap` (`renderSubject`) so concurrent render requests don't race; `Commands` uses the same pattern with `exhaustMap` to drop overlapping execute requests while one is in flight.

### DB connection & auth

`DbConnections.getConnectionWrapper()` lazily opens a connection per `key`, retrying up to `MAX_CONNECT_ATTEMPTS` times for a working password: it reads a cached password from `Secrets` (VS Code `SecretStorage`, keyed by `host-userName`, wiped on `deactivate()`), or prompts via `showInputBox` and caches it on success. The retry is bounded because not every failed connect is a bad password — an unreachable host would otherwise re-prompt forever — and a run that never opened is not cached as a session. Each `ConnectionWrapper` holds a `DbDriverConnection` plus a **separate worker connection** used for internal metadata queries (`useWorkerConnection: true`) so autocomplete/system-table lookups don't interfere with an open result cursor on the main connection. Query results are paged via `openCursor`/`fetch` using the `cursorFetchSize` setting; "Load More" in the results view calls `DbConnections.fetch()` again against the same cursor.

A user statement can be cancelled from its progress notification (or `DbConnections.cancelExecution(key)`), which calls the driver's optional `DbDriverConnection.cancel()` on the main connection. The ODBC driver calls node-odbc's `connection.cancel()` plus `statement.cancel()` on whichever cursor statement is busy (SQLCancel; the statement rejects with SQLSTATE HY008 and reports ERROR like any failure, without closing the session). Cursors are opened through `createStatement()`/`prepare()`/`execute({cursor: true})` rather than `connection.query()` for this reason: DB2 for i usually does a query's work in the first fetch, and `connection.cancel()` only reaches a statement while `query()` is executing it. Only a busy statement is cancelled, since SQLCancel on an idle one can close its open cursor. A CALL is never offered Cancel, because node-odbc documents DB2 for i procedure calls as not cancellable. `execute()` resolves to an `ExecuteStatus`, and `Commands.runStatements` stops a batch at `CANCELLED`, which means the user asked to cancel even if the statement finished anyway.


A session's main and worker jobs must always have the same library list: the worker runs every internal lookup, including the few that resolve unqualified names through `*LIBL` (trigger dispatch's routing table). `DbConnections.setLibraryList()` (the results panel connection tab's Edit, which opens the shared Edit Schema List dialog in its `live` mode) sets the user portion with `CALL QSYS2.QCMDEXC(?)` and the `CHGLIBL` command bound as a value, on the main job first and then the worker. A worker failure puts the main job back before the error is thrown, it refuses while the main connection is executing or fetching, and QTEMP is always kept (`LibraryListUtils.keepQtemp`). The command never goes through `callProcedure()`: QSYS2 has two QCMDEXC overloads and node-odbc's parameter count check refuses every call. A library command the user runs themselves (`CALL QSYS2.QCMDEXC('ADDLIBLE ...')` or `values qsys2.qcmdexc(...)`, matched by `LibraryListUtils.isLibraryListCommand`) is caught on its RESULT in `execute()`: the main job's list is read back, copied to the worker if it changed, and announced with an info message. Either way `wrapper.info` is replaced with a new object and `LIBRARY_LIST_CHANGED` fires. The change lasts only as long as the connection, and it is a separate thing from the schema browser's persistent Edit Schema List overrides (`GlobalStates`): the two share the dialog component, not state. A user-run `CHGCURLIB`/`CHGSYSLIBL` is not mirrored to the worker yet.

A key that was closed on purpose stays closed: `close()` records it in `closedKeys`, and `getConnectionWrapper()` will not open a connection for it, so work already in flight when a session closes (a results render labelling its headings, the connection-time warm-up, a saved SQL import) can't quietly reopen a connection nothing will close again. Keys are reused (a reopened file has the same uri; schema browser and diagram sessions are keyed by config), so a user action is what reopens one: `allowConnect(key)` at the entry points (`Commands.runStatements`, `SchemasProvider.show()`, Refresh SQL Import, `reconnect`) or `connect(options)` where connecting is the whole action (diagram Connect, `promptToConnect`, View Table Details); `execute()` allows itself. A never-closed key still opens lazily on first access. A refused open looks exactly like a connection that couldn't be opened, which the failed-lookup rule under Metadata cache then keeps out of the cache. New user entry points that act on a possibly-closed key must call one of the two.

### Database drivers

Nothing above the driver layer knows about ODBC. `src/database/drivers/db-driver.ts` defines `DbDriver` (connect, plus optional `checkSetup`/`isSetupError`/`withSortSequence` hooks), `DbDriverConnection`, `DbCursor`, `DbResult` and `DbColumnDefinition`; `src/database/drivers/odbc/odbc-driver.ts` is **the only file in the repo allowed to import `odbc`**, and `src/database/drivers/driver-boundary.spec.ts` fails the unit suite if that ever stops being true. The import is a type-only import plus a lazy `await import('odbc')` at connect time, so a run on another driver never loads the native module. `DbResult` deliberately mirrors `odbc.Result` field for field so the ODBC driver returns its own object with no mapping layer.

`ConnectOptions` carries `{host, userName, password, connectionString?}` rather than a prebuilt ODBC string, so a future JDBC or IDB driver can assemble its own URL. Driver-reported error detail travels as `error.driverErrors` (read through `DbErrorUtils.extractDriverErrors()`), not `odbcErrors`. To add a driver: implement `DbDriver`, give it an `id`, and register it in `DbDrivers` (`extension.drivers`); a connection picks one via its `ConnectionConfig.driver`, overridden globally by the `DB2_WORKBENCH_DRIVER` environment variable, defaulting to `odbc`.

### Testing without a database

`FakeDriver` (`src/database/drivers/fake/`) is a `DbDriver` backed by a fixture instead of a SQL engine, which is what lets the integration suite run on a developer machine, in a container or in CI with no host, no ODBC driver manager and no credentials. A fixture is a `FakeDatabase` built by `defineFakeDatabase()` — schemas, tables, columns, keys, indexes, index advice, procedures and their rows (see `fixtures/sample-database.ts`). `CatalogResponder` answers the real `QSYS2` catalog statements (`SYSTABLES`, `SYSCOLUMNS2`, `SYSCST`, `SYSIXADV`, `LIBRARY_LIST_INFO`, `GET_JOB_INFO` and the rest) out of that fixture by matching the statement and its parameters, so production catalog queries are exercised rather than stubbed. A statement the fixture can't answer **throws** rather than returning nothing — a silent empty result is how a fake ends up asserting against nothing.

`FakeDriver` also applies writes: an `INSERT`/`UPDATE`/`DELETE` goes to `FakeDml` (`fake-dml.ts`), which changes the fixture's own rows so a row edit can be run and then read back (see `src/test/data-queries.test.ts`). It understands exactly the shape `RowEditUtils` generates — delimited identifiers, literal values, a `WHERE` of key equalities including the `RRN(table)` fallback — and throws on anything else. On the read side it honours `OFFSET`/`FETCH FIRST` and the synthetic `"$RRN"` select-list alias, and deliberately **ignores** `WHERE` and `ORDER BY`: evaluating arbitrary user-written SQL is where a fixture would turn into a database engine, so a test that cares about either clause asserts on the generated statement text instead. Each driver instance deep-copies the fixture it was given, so one test's writes can't reach the next test through the shared `SAMPLE_DATABASE`. Each connection the driver opens also keeps its own `FakeLibraryList` (`fake-library-list.ts`), the job's library list: it answers `LIBRARY_LIST_INFO` and applies `CHGLIBL`/`ADDLIBLE`/`RMVLIBLE` reaching it through QCMDEXC (a CALL throws CPF2110 for a missing library, the scalar function returns -1), and throws on any other CL command. Since a session's main and worker connections are separate driver connections, a test can read both jobs' lists back (`internalQuery` with `useWorkerConnection: false` for the main one) and assert they agree. `SAMPLE_DATABASE` declares QSYS2 with both real QCMDEXC overloads, off the library list, so a user CALL of it takes the overloaded-call path it takes live.

Tests add their own canned answers with `FakeDriver.Options.responses` (a regex plus rows or an error, a delay, or `untilCancelled` for a statement that waits for `cancel()` and then fails with HY008) and install them through `TestSupport.useDriver()`; `extension.drivers.register()` is the seam. `src/test/test-support.ts` also handles activation, the single test connection, event recording and `execute()`. Two things to know when writing a test: assert on `DbConnectionEvent`, since that is the real contract between the database layer and everything above it, and remember that opening a session fires its own catalog-lookup events on the same key — wait with `userStatementsOnly` rather than for "the next RESULT". Never sleep; arm a recorder before the call that triggers the event.

The suite runs through `.vscode-test.mjs`, which sets `DB2_WORKBENCH_DRIVER=fake` and `DB2_WORKBENCH_TEST_MODE=1` (test mode only bypasses the password prompt, via `Extension.isTestMode`) and points VS Code at throwaway `--user-data-dir`/`--extensions-dir` directories under `.vscode-test/` so a run neither collides with nor writes into the developer's own profile. Loading that config also deletes every downloaded VS Code build under `.vscode-test/` except the newest per platform (`pruneOldVsCodeBuilds`), since test-electron keeps each release it downloads (about 1 GB each) and never removes one. It also empties the test profile (`clearTestProfile`), which VS Code otherwise grows by a few MB of webview cache every run. `.github/workflows/test.yml` runs the four suites on Windows runners as parallel jobs (`lint_and_unit`, `webview_tests`, `webview_browser_tests`, `extension_host_tests`), uploading the browser suite's failure screenshots and this suite's test-profile logs as artifacts when a job fails; `.github/workflows/package.yml` builds the `.vsix` packages separately. `.github/workflows/release.yml` publishes to the Marketplace on a `v*` tag push: it checks the tag with `release-info.mjs` (tag matches `package.json`, `CHANGELOG.md` has the version's section, odd minor = pre-release channel), reruns `test.yml` and `package.yml` as reusable workflows, then waits for approval on the `marketplace` environment and publishes with `vsce publish --azure-credential`, signed in by `azure/login` as an Entra identity federated to that environment (no stored secret). The Marketplace has no trusted publishing (`--oidc`) backend yet. A Linux runner would need xvfb and Electron's shared libraries for this one (the unit and webview suites need neither, and the browser suite only needs `playwright install --with-deps --only-shell chromium`).

### SQL parsing is intentionally lightweight

`StatementParser.parse()` (`src/utils/statement-parser.ts`) strips comments, then dispatches to `SpParser` (regex-matches `{CALL proc(...)}` / `CALL proc(...)`, hand-parses parameters respecting quotes) or `SqlParser` (regex-based table-name extraction after `FROM`/`JOIN`/`UPDATE`/`INTO`) for everything else. This is not a real SQL AST — it's just enough to (a) know whether to `callProcedure` vs run a cursor query, and (b) know which tables are involved for autocomplete/column-label lookups. Keep new parsing logic consistent with this regex-based approach rather than introducing a full parser.

### Metadata cache

`MemoryCache` (`src/memory-cache.ts`) caches `SystemTable`/`SystemColumn`/`SystemIndexAdvice` lookups (from `QSYS2.SYSTABLES`/`SYSCOLUMNS2`/`SYSIXADV`), using `Sync.get()` (`src/utils/sync.ts`) to dedupe concurrent loads for the same key. Cache entries are keyed by the resolved connection config id (`getCacheIdentity()`), not by the caller's session `key` (typically a document uri) — so two sessions pointed at the same connection (e.g. two open SQL tabs, or a SQL tab and the schema browser) share one set of system-table lookups instead of each re-querying from scratch. `getCacheIdentity()` is async and goes through `DbConnections.getConnectionConfig()` (which establishes the connection if it isn't already open) rather than passively peeking at an existing one, so even the very first cache access for a brand-new session resolves to the real config id instead of temporarily keying off the raw session key; callers that already know the config id (e.g. `SchemasProvider`) can pass `configId` directly to skip that resolution. `DbConnections.close()` only calls `deleteConnectionCache()` once no other open session still references that config. It backs `StatementCompletionProvider` (autocomplete), `WorkbenchViewProvider`'s column header labeling (`resultHeadingLabels` setting: Short Name / Long Name / Description — Short Name is `SystemColumn.systemName`, Description is `SystemColumn.heading`, Long Name is the raw result-set column key itself, not a `SystemColumn` field), and the schema browser's Columns and Advised Indexes tabs. `SystemColumn.systemName`/`.sqlName` hold DB2's two column names (short "system" name vs. long SQL name, e.g. `EMNO` vs. `ACCT_EMPLOYEENO`) — don't confuse which is which when adding a new consumer. `getIndexAdvice()`'s per-table cache accepts a `forceRefresh` flag (used by the Advised Indexes tab's manual refresh and after running generated DDL like Create Index) to bypass a stale cached entry and recheck `SYSIXADV`'s live state.

No cache slot depends on a job's library list. The table, view and routine lists (`CatalogQueries.listTables`/`listViews`/`listRoutines`) always name the schemas they cover (`schema in (?, ...)`, chunked by `chunkSchemaNames`) and never join `QSYS2.LIBRARY_LIST_INFO`, and each schema keeps its own slot. `getTables()`/`getViews()`/`getRoutines()` with no schema compose the session's list per call from its own `ConnectionInfo.schemas`, in list order, out of those slots - so two sessions on one config with different (or changing) library lists each see their own list while sharing every schema's rows. Don't add a whole-list slot or a `Sync.get` key for the composed list; it would hand one session another's list.

Every per-table lookup (`getColumns`/`getTableKeys`/`getForeignKeys`/`getIndexes`/`getIndexAdvice`/`getTriggers`, and the `TableQueries`/`IndexQueries` methods behind them) takes `tables: TableTarget[] | TableTarget` — one table is a one-element batch, not a separate code path, widened with `ArrayUtils.toArray()`. They all funnel through `MemoryCache.loadTableEntities()`: each table keeps its own cache slot (so the requested set can change without invalidating what's already cached, and a table cached as "no rows" is a hit), and only the tables missing from cache are queried, in one statement built by `src/database/queries/table-predicates.ts` (`toTableTargets`/`buildTablePredicate`/`chunkTableTargets`/`queryByTableTargets` — pure, unit tested, chunked at `MAX_TARGETS_PER_QUERY`). Because a batched statement interleaves every table's rows, each query selects its own owning schema/table columns and rows are attributed by those rather than by the request's parameters. Callers with several tables in hand (a diagram load, a statement's table list) should pass them all in one call rather than looping; the returned array is flat, grouped by the caller off each row's `schema`/`tableName`.

A failed lookup is not an empty one. The query classes run their catalog SQL through `runCatalogLookup()` (`src/database/queries/catalog-lookup.ts`), which throws `CatalogLookupError` where a bare `internalQuery()` would return nothing; `MemoryCache.load()` turns that back into `[]` for callers, after the point where a cache slot would have been written, so a transient failure is re-queried next time instead of remembered as "no rows".

### Program source and trigger dispatch

The Triggers tab's View Source and a routine's Program Source tab show the source a native program was compiled from. `ProgramQueries` (`src/database/queries/program-queries.ts`, pure helpers in `program-source.ts`) lists the recorded locations (`PROGRAM_INFO` for OPM, one per module from `BOUND_MODULE_INFO` for ILE, a member or an IFS stream file) and `readSources()` reads them. A member is read through a QTEMP alias (create, select, drop); a QTEMP location is the compile job's temporary copy and is never read. A failure reading one source is carried on that source, not thrown, so the other modules still show.

`readSources()` first runs one `SYSPARTITIONSTAT` statement saying which recorded members still exist. A member that's gone (typically compiled from a test library cleaned up after promotion) is replaced by a same-named copy elsewhere: `OBJECT_STATISTICS('*ALLUSR', '*FILE', ...)` finds the libraries holding the source file, then one `SYSPARTITIONSTAT` search in those (searching by member name alone takes minutes live). `chooseMemberCopy` prefers the program's own library, then the library list, then the most recently changed, and the source carries a notice naming the others, a warning when the copy changed after the module was compiled. No copy is an `unavailable` message, not an error. Each statement there is a union or batch, never one per member - keep it that way.

Those same lookups return each member's `LAST_CHANGE_TIMESTAMP`, and `MemoryCache.getSourceText()` reuses a member's text while that timestamp is unchanged, so an unchanged program costs one statement to reopen and an edited member shows straight away. Stream files, members whose timestamp lookup failed, and failed reads are never cached. The locations and the dispatch resolution below are looked up every time.

An external trigger's program may be a dispatcher (Trigger Mediator's `TG_MED`, or a home-grown one) that looks up the real handler in a routing table at run time - nothing in the catalog links the two. `TriggerDispatchQueries` (pure steps in `trigger-dispatch.ts`) finds it from what the catalog does record, with no product, table or column name hard-coded: the tables the dispatcher's static SQL reads (`SYSPROGRAMSTMTSTAT`, extracted with `SqlParser`), their rows naming the trigger's table in a character column, pairs of that row's values that name an existing `*PGM`/`*SRVPGM` (libraries confirmed through `SYSSCHEMAS` first, so a value that only looks like one never produces a failing lookup), and a `*SRVPGM` export (`PROGRAM_EXPORT_IMPORT_INFO`) the row also names. A row the dispatcher's own `column = 'literal'` conditions skip (`WHERE TRACTIVE = 'Y'`) still resolves, marked `unselected`, and the dialog shows a warning. Two live traps: a character column shorter than the table name must not be compared to it (ODBC types the marker by the column, and binding into a CHAR(1) fails the statement with CWB0111), and the routing table resolves through the *connection's* library list. Handler sources show first in the dialog; a resolution failure leaves them out rather than failing it. Dispatchers that read the routing table with native I/O (no statement text) aren't covered.

### Packaging bundles the extension host code

Development, debugging and every test suite run the multi-file `tsc` output in `out/`. Only packaging bundles it: `vscode:prepublish` runs `esbuild-extension.mjs`, which overwrites `out/extension.js` (`main`) with a minified ESM bundle, plus a chunk under `out/chunks/` for each dynamic `import()`, and `.vscodeignore` ships nothing else from `out/` except `out/vendor/`. Code splitting is how a large library only one feature needs stays out of activation: `@dbml/core`, about 15 MB of the bundle, is `await import()`ed inside `dbmlFormat.import()` (which is why `SchemaFormatConverter.import()` is async) - load any similar library the same way rather than with a top-level import. The bundle overwrites `main` rather than living elsewhere because the integration tests import the `extension` singleton from `out/extension.js`; the host must activate that same module, or the tests would drive a second instance. `postbuild-exe` reruns `tsc` to put the multi-file output back, but a `tsc -watch` already running while you package will not, so restart it before debugging. `vsce publish` without `--packagePath` also bundles and leaves the bundle in place.

Everything the bundle contains is a `devDependency`; `dependencies` holds only what must ship in `node_modules`, because `vsce` copies exactly that. Today that is `odbc` alone: it loads a native binary, so it is `external` and stays a lazy `await import('odbc')`. A new runtime library goes in `devDependencies` unless it can't be bundled. dt-sql-parser stays in its own pre-bundled `out/vendor/` file, loaded only through `src/dt-sql-parser.ts`, which sits at the root of `src/` so its relative path resolves the same from `out/dt-sql-parser.js` and from the bundle. `vscode:prepublish` ends with `third-party-notices.mjs`, which writes `THIRD_PARTY_NOTICES.txt` (gitignored, shipped in the package) from the metafiles all three esbuild builds write to `out/metafiles/`, so it lists exactly what was bundled. It fails the package on a license outside its `ALLOWED_LICENSES`, or on a dual license with no entry in `LICENSE_ELECTIONS` (`elkjs` is used under EPL-2.0, never GPL): a new dependency under an unreviewed license stops the build rather than shipping. Every packaged `.vsix` is platform-specific because of `odbc`; `.github/workflows/package.yml` builds one per target on a matching runner.

### Webviews are React apps bundled by esbuild

Each webview surface under `webviews/{bundleName}/` (`connections`, `results`, `formatting`, `schemas`) is a small React app, bundled by esbuild to `dist/webviews/{bundleName}/index.js` and mounted into an HTML shell built by `WebviewHtmlUtils.getReactWebviewHtml()` (see e.g. `ConnectionEditorProvider.getPanelHtml()`, `SchemasProvider.show()`). Data the extension already has at panel-creation time is embedded once as `window.__INITIAL_STATE__` (read via each bundle's `initial-state.ts`) rather than round-tripped over a message. Two-way communication (needed once a webview must ask the host for more data or trigger an action, e.g. "Load More" or a refresh button) goes through a typed `command`-discriminated message union in `src/webview-messages/{bundle}-messages.ts` — an `Outbound` union (webview → host, posted via each bundle's own `webviews/{bundle}/vscode-api.ts` wrapping `acquireVsCodeApi()`) and an `Inbound` union (host → webview, received via `window.addEventListener('message', ...)` and handled in the bundle's `app.tsx`) — with the provider's `panel.webview.onDidReceiveMessage`/`postMessage` on the host side. Not every webview needs this: the schemas webview, for example, only gained it once a sub-tab needed to lazily fetch data the initial state didn't already carry.

Webview components are tested with vitest + `@testing-library/react` in jsdom (`npm run test:webviews`, config in `webviews/vitest.config.ts`): co-located `*.spec.tsx` next to the component, importing `describe`/`it`/`expect` from `vitest` explicitly (no globals — the layout guard relies on that import). No browser and no display are involved, so it runs headless anywhere Node does. `webviews/test-support/` supplies the seams: `setup.ts` installs an `acquireVsCodeApi()` stub before any bundle module loads (each bundle's `vscode-api.ts` acquires it once at import time and caches it, so the stub is reset in place between tests, never replaced); `postedMessages()` returns what the webview posted, structured-cloned as a real `postMessage` would; `postFromHost()` dispatches an `Inbound` message as a window `message` event inside `act()`; `renderWebview()` embeds a JSON round-tripped `__INITIAL_STATE__` and mounts the component in the same providers its `index.tsx` uses; `useFakeTimeouts()` fakes `setTimeout` for a debounce test without hanging userEvent (pair it with `userEvent.setup({ delay: null })`). vitest does not typecheck, so a spec fixture missing a required field fails at runtime or only in `tsc -p webviews` — build fixtures through a typed helper. Assert on the message contract and on rendered text/roles. jsdom has no layout: every element measures 0x0 and canvas `getContext()` returns null, so virtualized rows (react-virtual, React Flow) render nothing and column-width measurement is skipped. `useFakeLayout()` (`test-support/fake-layout.ts`) supplies the viewport and row heights react-virtual reads, plus a `scroll()` that sets scrollTop/clientHeight/scrollHeight and fires the scroll event — enough to test which rows a window renders and what a scroll handler (e.g. Load More) decides. It cannot catch a layout bug such as a scroll container with no bounded height, since the height comes from the stub rather than the stylesheet; that still needs a real browser. React Flow (the diagram) renders under the same stub, but calls `onInit` from a `setTimeout`, and until it fires the canvas sits on its 'cluster' zoom tier with every table hidden — wait for the table nodes before asserting. Click a node's drag-handle header with `fireEvent.click`, not userEvent: d3-drag's mousedown handler dereferences `event.view`, which a jsdom-synthesized mousedown leaves null. Dragging itself (move/resize) isn't testable here — that is what the browser suite is for (below). A closing MUI dialog leaves the rest of the page `aria-hidden` until its exit transition ends, which hides it from every role query — `waitFor` the dialog to be gone before querying past it.

What jsdom can't do goes in the real browser suite (`npm run test:webviews:browser`, config in `webviews/vitest.browser.config.ts`): co-located `*.browser.spec.tsx`, run by vitest browser mode in headless Chromium through Playwright, at a fixed 1200x800 viewport. The jsdom config excludes that suffix. Headless needs no display, so it runs on a developer machine and in CI alike; the one prerequisite is the browser download (`npx playwright install chromium`), which `npm ci` does not do. Its setup (`test-support/browser-setup.ts`) shares the VS Code API stub and per-test reset with `setup.ts` through `test-support/common-setup.ts`, but none of the jsdom shims, and gives the body the same zero margin the webview HTML shell does. The same `renderWebview()`/`postedMessages()` seams and Testing Library queries work unchanged. Drive pointer gestures with `userEvent.dragAndDrop()` from `vitest/browser` (real Playwright mouse input; `sourcePosition`/`targetPosition`/`steps`/`force` pass through), not Testing Library's userEvent. React Flow starts a drag only once the pointer passes its 1px threshold and measures from that move, so the whole first step is lost — use small steps and allow one step's worth. fitView chooses the zoom, so read it from the `.react-flow__viewport` transform rather than assuming one. The diagram's bottom-right panel (controls and overview map) sits above the canvas, and fitView leaves the diagram's bottom-right corner beneath it, so pan a node's bottom-right resize handle clear before pressing it. Fonts differ between machines, so assert on relationships with a tolerance (moved by the dragged distance, reported position matches the on-screen one), never on absolute pixels or screenshots. A failing test leaves a screenshot under `webviews/.vitest/attachments/` (gitignored, kept as a CI artifact, and emptied at the start of every run by `test-support/clear-attachments.ts`, since vitest itself never clears it). `test-support/schema-tree-layout.ts` checks that the shared SchemaTree really virtualizes inside a host's layout (bounded scroll container, a window of rows, no page scroll); each host's `app.browser.spec.tsx` runs it against its own App, since the height comes from the host.

### Config layering

Three separate persistence mechanisms, each with a distinct purpose — don't mix them up:
- `Configurations` (`src/configurations.ts`) — user/workspace settings under `db2-workbench.*` (`connections`, `cursorFetchSize`, `historyCount`, `resultHeadingLabels`). `connections` (the `ConnectionConfig[]` array) is both a VS Code setting and the source of truth for the connections tree view — keep `package.json`'s `contributes.configuration` schema for `db2-workbench.connections` in sync with the `ConnectionConfig` interface. `dataEdit.*` (the schema browser Data tab's Add Row defaults, shaped by `DataEditSettings` in the pure `src/utils/data-edit-defaults.ts`) is edited from the Data tab's Settings dialog as well as Ctrl+,: the webview posts `saveDataEditSettings`, and `SchemasProvider`'s configuration listener pushes `dataEditSettingsChanged` back to every open panel, so a change made anywhere reaches them. Its type list (`DataEditDefaults.APP_DEFAULTS`) must stay in sync with the `defaultValues` schema's properties.
- `GlobalStates` (`src/global-states.ts`) — `context.globalState`, for extension-managed values not meant to be user-editable settings (e.g. `lastActiveHost`).
- `Secrets` (`src/secrets.ts`) — `context.secrets`, DB passwords only, keyed by `host-userName`.

### Commands

`Commands` (`src/commands.ts`) registers all `db2-workbench.*` commands and is where editor-context/menu commands (`executeSql`, `executeAllSql`, connection CRUD) are wired to `Extension` services. New commands should be added here and declared in `package.json`'s `contributes.commands`/`menus`/`keybindings`.

## Conventions

- Plain language features for the simple cases: `x == null`/`x != null` for absent values (the `eqeqeq: smart` lint rule allows exactly this), `??`/`??=` for defaults and lazy init, `!array?.length` for an absent-or-empty array, `value?.trim()`. Shared helpers live in `src/utils` for what has no one-liner: `StringUtils.isBlank/isNotBlank/equalsIgnoreCase/beginsWithIgnoreCase/default/trim` (trim's options collapse inner whitespace or turn blank into undefined), `ArrayUtils.toArray/toMapOfArrays/removeIf`, `TryUtils.tryAsync/forgetPromise`, `Sync.get`, `SubscriptionManager`, and `Nullable<T>` (`T | undefined`, not null). Add a helper there, pure and free of `vscode`, rather than a feature-local copy - and don't add one for something the language already says in a line.
- Namespaces are used alongside classes for co-locating related types/enums (e.g. `export namespace DbConnections { export interface ExecuteOptions ... }`) — follow this pattern instead of a separate types file when adding options/enums tied to a specific class.
- Column names go through `ColumnNameUtils` (`src/utils/column-name-utils.ts`, pure, importable from webviews). A raw row key, catalog name or imported name is an identity, never display text: show a column with `labels()`/`displayName()` (or `labelForKey()`/`labelsForKey()` when a webview only holds the host-built label map), which follow the `resultHeadingLabels` setting. To decide whether a name refers to a column, use `matches()`/`find()`/`findSystemColumn()`/`buildResolver()`, which try every name form (identity, short, long) case-insensitively, never the description, and never depend on the setting. Don't hand-roll `systemName`/`sqlName` comparisons or `columnLabels[key]?.[0] ?? …` fallbacks.
- rxjs `Subject` + `concatMap`/`exhaustMap` is the established pattern for serializing or debouncing async work (renders, SQL execution) — reach for it instead of ad hoc boolean "isBusy" flags.
- TanStack Table-backed data tables (schema browser tabs, results grid) never wrap cell content, and alternate row background colors for readability. Rows should not grow tall from wrapped text; rely on horizontal scrolling instead. Any per-row context menu (e.g. Advised Indexes' "⋮" menu) belongs in a column with `id: 'actions'` frozen to the right edge so it's reachable without scrolling. For a plain (non-virtualized) `<Table>`, use `webviews/shared/components/data-table.tsx`'s `<DataTable table={reactTable} />`, which renders the sortable header, nowrap + zebra-striped body, and freezes the `actions` column automatically — build the `useReactTable` instance in the tab component as usual and hand it to `<DataTable>` instead of hand-rolling `TableHead`/`TableBody`. Virtualized grids (the results grid's `DataTab`, the schema browser's Data tab) use `DataTable` too, passing a `virtualizer`. Numeric columns right-align their body cells (never the header) via `meta: { align: 'right' }`. A grid whose cells are expensive (inline-edit inputs) passes `rowRenderKey` so a keystroke re-renders only the edited row, not every visible input — its cells and `rowSx` must then depend only on `row.original` plus what that key captures.
- Dependency versions are pinned exactly. To add or bump one, edit the version in `package.json` by hand and then run `npm install`; never `npm install <pkg>@<version>` / `--save-dev`. Those rewrite the whole file with npm's own formatting, which expands the deliberately one-line-per-type `dataEdit.defaultValues` schema (and any other compacted JSON) into a large diff. Check that `git diff package.json` shows only the lines you meant to change. When the bump is `@vscode/vsce`, also diff `npx vsce ls` before and after to confirm the packaged file list hasn't changed.
